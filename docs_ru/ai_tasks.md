# AI-задачи и контроллеры движений

Как поведение NPC структурировано на уровне C++. Кооперируют три слоя:

1. **TAB** (Task Animation Bone) — примитивные задачи **на основе
   анимации** для отдельных каналов. «Идти вперёд», «повернуться лицом»,
   «проиграть lookAt-анимацию». Каждый TAB запускает соответствующий
   анимационный трек на риге костей актора (см. [animation.md](animation.md)).
2. **CAB** (Composite Animation Behaviour) — **контейнер задач**
   более высокого уровня, секвенирующий TAB'ы в многошаговые действия.
   «Подойти к игроку, затем атаковать» — это CAB.
3. **APMotion** — служебные классы для **плавной интерполяции**
   значений позы актора между двумя TAB'ами (чтобы переходы не были резкими).

Это акторный планировщик движка; он независим от (и работает поверх)
скриптового механизма `task`, описанного в [tasks.md](tasks.md). Скрипты
управляют AI, делая `RunTask` для нужных классов TAB или CAB.

```

ICABTask.h            — CAB-specific interface

TABBase.{cpp,h}       — TAB factory and base type

CABBase.{cpp,h}       — CAB base, sequencer
CABTasked.{cpp,h}     — script-driven CAB

APMotionBase.{cpp,h}        — abstract motion interpolator

APMotionPlay.{cpp,h}         — playback driver

TaskBase.{cpp,h}      — generic task base (for non-AI tasks too)
TaskScripted.{cpp,h}  — task hosting a script context
```

## 2. Каталог TAB'ов

`CTABBase` (`TABBase.h:19`) объявляет список классов фабрики — ровно
**13 конкретных TAB'ов**:

| Класс                          | Что делает                                                           |
|--------------------------------|----------------------------------------------------------------------|
| `CTABFace`                     | Повернуть голову лицом к цели. Запускает LookAt по подмножеству костей лица. |
| `CTABFadeAnimation`            | Сводит одну анимацию **из**, пока следующая сводится **в**.          |
| `CTABFollowPath`               | Идти вдоль `CScenePath` (последовательность вэйпоинтов). Использует навмеш. |
| `CTABInterpolateAnimation`     | Плавно интерполирует от текущей позы к позе целевой анимации.        |
| `CTABLockAnimation`            | Удерживает позу одного ключевого кадра (заморозка на определённом кадре анимации). |
| `CTABMoveDir`                  | Двигаться в заданном направлении с заданной скоростью.               |
| `CTABMoveLine`                 | Двигаться по прямой к целевой мировой позиции.                        |
| `CTABPlayAnimation`            | Проиграть один именованный анимационный трек до конца.               |
| `CTABPlayLook`                 | Проиграть позу «look at» (процедурную — использует IK костей, не запечённую анимацию). |
| `CTABPlayLookLSH`              | То же, что `CTABPlayLook`, но управляет лицевым риггом LSHead.       |
| `CTABPlayLookRel`              | «Look at» с целью, заданной относительно локальной системы координат актора. |
| `CTABPlayWalk`                 | Зацикленная walk-анимация, темп которой определяется скоростью движения (избегает скольжения ног). |
| `CTABRotate`                   | Вращаться на месте к курсу.                                          |

Все наследуются от `IBaseTask`. Фабрика (`CTABBase::TTABFactory`)
построена из этого списка типов (`TYPELIST_13(...)`) — стирающая типы
регистрация во время компиляции, чтобы скриптовая сторона могла
сконструировать любой TAB по factory ID без ручных switch-таблиц.

### 2.1 Общий API TAB

Каждый TAB предоставляет:

- `Update(dt)` — вызывается каждый игровой тик для продвижения состояния.
- `IsFinished()` — когда этот TAB достиг своей цели.
- Конструктор, принимающий параметры, специфичные для его задачи
  (целевая позиция, имя анимации, скорость, …).
- Пары `SaveObject` / конструктор загрузки состояния (чтобы сохранение
  посреди ходьбы возобновлялось корректно — см. [save_format.md](save_format.md)).

## 3. CAB — композитные поведения

`CCABBase` (`CABBase.cpp`) — это очередь TAB'ов (или вложенных CAB'ов),
выполняемых по порядку. CAB предоставляет:

- `AddTask(IBaseTask *)` — добавить шаг.
- `Cancel()` — прервать текущий шаг и остановиться.
- `Update(dt)` — продвигает голову очереди; снимает её при завершении
  и запускает следующую.

`CCABTasked` (`CABTasked.cpp`) — это скрипто-привязываемый подкласс:
он держит `IScriptContext` и эмитит события `OnComplete` / `OnCancelled`
обратно в скрипт, когда завершается каждый шаг или весь CAB.

Типичное поведение NPC:

```
ApproachAndKill(target):
    CAB:
        TABFollowPath(path to target, speed=walk)
        TABMoveLine(within attack range, speed=run)
        TABRotate(face target)
        TABPlayAnimation("attack_a")
        TABPlayAnimation("idle")
```

Скрипт делает `RunTask` для CAB и ждёт события `OnComplete`.

## 4. APMotion — плавная интерполяция

При переходе между двумя TAB'ами, которые оба затрагивают одну и ту же
кость или значение позы, резкая смена выглядит плохо. Классы `APMotion*`
реализуют **поканальное ease-in/ease-out**-смешение:

| Класс                       | Роль                                                  |
|-----------------------------|-------------------------------------------------------|
| `CAPMotionBase`             | Абстрактный; определяет `Start`, `Update(dt)`, `IsDone`. |
| `CAPMotionInterpolate`      | Линейная или smoothstep-интерполяция между двумя значениями. |
| `CAPMotionPlay`             | Движение по времени (продвигает кривую с фиксированной скоростью). |

Используется как внутри TAB'ов (например, `CTABInterpolateAnimation`
использует `CAPMotionInterpolate` для смешивания позы костей), так и
автономно скриптами, которые хотят плавно изменить значение, не
относящееся к актору (камера, оверлей затухания).

## 5. Подключение pathfinding

`CTABFollowPath` вызывает `CPathFinding::FindPath(src, dst, …)`
(см. [`formats/pfd.md`](formats/pfd.md)) на старте, затем идёт по
возвращённому `TPath` вэйпоинт за вэйпоинтом, запрашивая прямолинейное
движение (семантика `CTABMoveLine`) между вэйпоинтами. Позиция актора
проверяется каждый тик относительно следующего вэйпоинта; по прибытии
индекс продвигается.

Если путь заблокировался посреди движения (событие `OnClearPath`),
задача follow-path перезапрашивает у поискателя пути новый маршрут.

## 6. Куда подключаются скрипты

На стороне скриптов актор «владеет» нулём или больше работающими
задачами. Семейство `taskbase.sci` (в `Game/script_sources/`) оборачивает
C++-API TAB/CAB в типы `task`, которые исходник `.sc` может расширять.
Типичный паттерн:

```c
task TMoveToPlayer : TTaskBase {
    void OnStart(void) {
        @RunCAB(self());                       // create empty CAB
        @CABAdd(@TABFollowPath(playerPath));   // queue follow-path
        @CABAdd(@TABRotate(facePlayer));       // then face player
    }
    void OnComplete(void) {
        // queue exhausted — fire next behaviour
    }
}
```

Точные имена host-API находятся в [script_api.md](script_api.md).

## 7. Взаимодействие с сохранениями

Каждый TAB и CAB реализует пары `SaveObject` /
`(const char *&, ILoadStateData *)`-конструктор. Сначала пишется ID
фабрики (зарегистрированный через `TFClassList` выше), затем состояние
конкретного класса. Это означает:

- Персонаж посреди ходьбы корректно возобновляется из сохранённой игры.
- Многошаговый CAB возобновляется на правильном шаге.
- Интерполирующий APMotion возобновляется посреди смешения (текущее `t` сохранено).

## 8. Зачем три слоя (TAB / CAB / APMotion)?

Каждый слой отвечает на один вопрос:

- **TAB**: «Какую одну вещь актор должен сделать сейчас?» — примитив.
- **CAB**: «В каком порядке актор должен сделать несколько вещей?» —
  последовательность.
- **APMotion**: «Как одно числовое значение плавно становится другим
  числовым значением со временем?» — кривая.

Разделение их означает, что скриптам нужно знать только о CAB'ах,
TAB'ы — это переиспользуемые строительные блоки, а APMotion'ы можно
переиспользовать внутри любого TAB или напрямую скриптами без
притаскивания инфраструктуры анимации.
