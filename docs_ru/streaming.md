# Стриминг ассетов и асинхронный I/O

Как движок грузит тяжёлые ассеты (меши, текстуры, сцены), не
блокируя главный поток.

- **Пул задач**: `IStreamerPool` (`Engine/Core/IStreamerPool.h`) —
  управляет фиксированным числом фоновых воркер-потоков.
- **Дескриптор задачи**: `IStreamerJob` (`IStreamerJob.h`) — одна
  единица фоновой работы.
- **Драйвер**: `IStreamer` (`IStreamer.h`) — очередь подачи на
  подсистему (одна на сцену акторов, одна на текстуры и т.д.).
- **Хелперы стриминговой загрузки**: `CStreamLoading` в
  `Game/Engine/StreamLoading.cpp` — адаптирует стример к потоку
  загрузки сцены.
- **AsyncIO** (`Game/Game/AsyncIO.cpp`): низкоуровневые примитивы
  чтения файлов.
- **AsyncStream** (`Game/Sound/AsyncStream.cpp`): тот же шаблон, но
  для воспроизведения Ogg Vorbis.

---

## 1. Модель потоков

```
Главный поток:
    тик игры
        → ставит IStreamerJob в IStreamer
    рендеринг, ввод, скрипты

Пул воркеров (N потоков, фиксируется при старте):
    достаёт следующую задачу из приоритетной очереди
    выполняет I/O + декомпрессию + разбор
    по завершении выставляет флаг готовности (атомарный)

Главный поток (следующий тик):
    опрашивает завершённые задачи
        → публикует их результаты (например, меняет плейсхолдер-меш на загруженный)
```

Игровая логика движка в остальном **однопоточна**. Воркеры трогают
только выходной буфер своей задачи и входной файл (который
memory-mapped read-only из VFS-архива). Синхронизация — через
атомарный флаг завершения, а не через локи.

---

## 2. Жизненный цикл задачи

`IStreamerJob` обычно владеет:

- Целевым `IMMLoadObject *` (memory-mapped файл из VFS).
- Скретч-буфером для распакованного payload'а (вывод zlib, массив
  вершин меша, …).
- Атомарным флагом «ready».
- Указателем на целевой слот на стороне main (куда будет установлен
  разобранный объект).

Main → background:

```cpp
IStreamerJob *job = …;
job->Start(streamerPool);    // ставит в очередь; сразу возвращает управление
…
// следующий тик
if (job->IsCompleted()) {
    actor->m_pGeometry = job->TakeResult();   // передача владения
    delete job;
}
```

Если задача **брошена** (актор выгружен до того, как пришли данные),
движок выставляет флаг отмены; воркер всё равно доделает текущий
шаг, но по завершении выбросит результат.

---

## 3. Приоритет

`IStreamer::Submit(job, priority)` кладёт задачу в min-heap,
ключевой по приоритету. `CSceneOutdoor` пересчитывает приоритет
для каждого актора каждый тик исходя из **дистанции до камеры
игрока** (`FillStreamData(...)` в `SceneOutdoor.cpp`). Чем ближе
актор, тем выше приоритет — так следующими грузятся именно те
ассеты, которые игрок вот-вот увидит.

---

## 4. `CStreamLoading` — адаптер сцены

Для каждой сцены `CStreamLoading` пакетирует задачи по данным
акторов:

- При загрузке сцены он проходит по списку акторов и ставит по
  одной задаче на каждого.
- Каждая задача открывает noext placement-файл актора в
  `Actors.vfs`, разбирает ведущий u32-дискриминатор типа и вызывает
  `Load(IActorStreamData *)` соответствующего класса актора, чтобы
  заполнить stream-data (тяжёлое: меш, oct-tree, блобы коллизии).
- Когда задача завершается, `PerformLoad(pStreamData)` актора в
  main-потоке прикрепляет стримленные данные к живому актору.

Именно поэтому у каждого класса актора **двухстадийная загрузка**:
дешёвый конструктор, который просто запоминает параметры, и
тяжёлый `PerformLoad(pStreamData)`, который потребляет либо
стримленные данные (если вызван из обработчика завершения стримера),
либо свежепрочитанные (если вызван синхронно без стримера).

Канонический пример — `ActorStatic.cpp:342`:

```cpp
void CActorStatic::PerformLoad(IActorStreamData *pData) {
    if (!pData) {
        // синхронный fallback — стример не используется
        ...
    } else {
        // данные предоставлены стримером — просто клонируем
        m_pExactMeshData = pStreamData->m_pExactMeshData->Clone();
        m_pExactOctTree  = pStreamData->m_pExactOctTree->Clone(m_pExactMeshData);
        ...
    }
}
```

## 5. AsyncStream — тот же шаблон для звука

`CAsyncStream` (`Game/Sound/AsyncStream.cpp:59`) использует
практически идентичную модель для воспроизведения Ogg Vorbis (см.
[`formats/ogg.md`](formats/ogg.md)). Фоновый поток:

1. Открывает Ogg через `ov_open_callbacks` поверх
   memory-mapped указателя VFS.
2. Декодирует ~ 0.25 с в один из четырёх буферов OpenAL.
3. Передаёт буфер OpenAL для воспроизведения.
4. Спит, пока OpenAL не освободит буфер.

Главный поток никогда не блокируется на декоде аудио.

## 6. Давление по памяти

У пула стримера нет встроенного учёта памяти — задачи аллоцируются
из кучи движка и полагаются на то, что путь выгрузки актора
освободит данные, на которые больше нет ссылок. «Малый файловый
кеш» на уровне VFS ([vfs_format.md §5.2](vfs_format.md))
ограничивает рост памяти от перезагрузок мелких ассетов, но большие
меши грузятся один раз на экземпляр актора.

Реальное узкое место, с которым движок справляется, —
**дедупликация мешей на уровне oct-tree**: 
`CCollisionManager::CreateMeshData` и `CreateOctTree` возвращают
клонируемые объекты, а `CActorStaticPerformLoad` зовёт
`Clone(m_pExactMeshData)`, так что несколько экземпляров актора с
одним и тем же мешем разделяют один и тот же базовый буфер.

## 7. Сценарии отказа

| Симптом                                  | Причина                                                          |
|------------------------------------------|------------------------------------------------------------------|
| Актор вылезает с задержкой (виден плейсхолдер) | Приоритет задачи ниже, чем подсказывает ранжирование по дистанции до камеры. |
| Хитч при загрузке сцены                  | Сработал синхронный fallback (стример недоступен / выключен).    |
| Заикание звука                           | Underrun буфера OpenAL (воркер-поток не успевает).               |
| «File not found» в логе + пропавший актор| Файл актора упомянут в `.isc`, но отсутствует в `Actors.vfs`.    |

Подсистема лога (`Game/Game/LogFile.cpp`) записывает каждое
событие асинхронной загрузки в debug-сборках.
